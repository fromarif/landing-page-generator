# The engine class prefix

One knob: `prefix` in `src/config/site.ts` (default `app` → `app-loader`,
`app-cursor`, …). It drives three layers.

| Layer | How |
|---|---|
| markup + JS | `cls()` / `sel()` from `src/scripts/core/names.ts` |
| SCSS | `$prefix` from `src/styles/_prefix.scss`, generated by `astro.config.ts` |

It covers **everything** in the DOM: engine components (`-loader`, `-cursor`,
`-navbar`, `-footer`), the cursor's runtime-built children, the `<html>` flag, and
the sections (`-hero`, `-showcase`, `-prose`). The one thing written literally is
a `-modifier` state — `-inverse`, `-pointer`, `-text` — which hangs off an
already-prefixed block.

Rules:

- Never write an engine class as a string literal. The point is that markup and
  the engine's querySelectors can't drift apart.
- Engine style blocks open with `@use '../styles/prefix' as *;` and must be
  `<style lang="scss">` — a plain `<style>` never goes through Sass.
- `prefix` must stay a **plain string literal** in `site.ts`. The hot-update hook
  re-reads it out of the file because the imported module is cached, so a
  constant or computed value won't be picked up. It warns to the console rather
  than failing silently.
- `src/styles/_prefix.scss` is generated and gitignored. A cold build recreates
  it at config load, so a fresh clone and CI are fine.

## Changing it in dev triggers a full reload

Editing `prefix` while `npm run dev` is running rewrites the generated partial,
which invalidates every style block that `@use`s it. A CSS-only HMR update is not
enough here: a page reached by client-side navigation never gets those styles
re-injected and renders with the right class names and no styles at all.

So the plugin in `astro.config.ts` watches the generated partial and answers a
change to it with `hot.send({ type: 'full-reload' })` instead of an HMR patch.
The reload keeps the current route.

The hook is split deliberately — `site.ts` changes write the partial, and the
*partial's* own change is what sends the reload. Sending it straight from the
`site.ts` hook would race Vite's watcher and could reload before the new value
had been picked up.

Measured: sitting on `/about/` reached by a click, changing the prefix reloads
the page on its own, stays on `/about/`, and comes back fully styled with no
stale-prefix classes. Client-side navigation after that behaves normally.

Production never had this problem — there the styles are one linked stylesheet
rather than injected `<style>` tags. Verified against `npm run preview`.

## Do not replace this with `additionalData`

The obvious approach — `vite.css.preprocessorOptions.scss.additionalData` —
is silently broken. The string is baked in when the config is *evaluated*, once,
at dev-server startup. Editing `site.ts` then hot-reloads the TS side (markup and
JS switch to the new prefix) while the compiled SCSS keeps the old one: markup
says `.fa-navbar`, CSS still says `.app-navbar`, and every engine component loses
its styles with no error anywhere.

A dev-server restart does not fix it either — Vite restarts with the same
already-resolved config object. This was tried and rejected.

Writing a real file works because it puts the prefix in Vite's module graph: the
style blocks `@use` it, so changing it invalidates and recompiles them the normal
way. **Verified** by editing the prefix live with the server running — markup and
CSS both followed, with zero stale rules from the previous prefix.
